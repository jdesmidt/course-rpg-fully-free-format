# NoxDB

NoxDB is an open source RPG framework (by Niels Liisberg) for working with JSON, XML and SQL through one single approach. A document, JSON or XML, is represented as an in-memory tree of "nodes", addressed through node path expressions similar to XPath. It is available on GitHub: https://github.com/sitemule/noxDB, that repository also has an `/examples` directory with additional sample programs.

NoxDB ships two copybooks that are functionally identical: `jsonparser.rpgleinc` (every routine prefixed `json_`) and `xmlparser.rpgleinc` (the exact same routines, prefixed `xml_` instead, calling the very same underlying functions). Once a document is parsed into a node tree, every routine that reads, changes or writes that tree works exactly the same way whether it started out as JSON or XML, so everything in this chapter applies equally to both, only the prefix changes. `jsonparser.rpgleinc` itself is thoroughly documented, with a comment block above every single routine, it is worth reading directly for details beyond this chapter.


## Getting started : binding and including

```
   ctl-opt bnddir('JSONPARSER');

   /copy qcpysrc,jsonparser
```

- `bnddir('JSONPARSER')` binds the service program(s) that implement NoxDB, `bnddir('XMLPARSER')` does the same for the `xml_` prefixed routines, `bnddir('JSONXML')` includes both at once.
- `/copy` (or `/include`) pulls in the matching prototypes.


## Node path expressions

Most routines take a node path expression to say which part of the tree to work on: `/` or `.` can both be used as a delimiter (`/customer/name` is the same as `customer.name`), an array element is addressed with brackets (`/customer/address[0]/street`), and `[UBOUND]` addresses the last element of an array. Passing `''` or `*null` as the path refers to the node itself, rather than one of its children.


## Parsing a document

```
   dcl-s pDoc pointer;

   pDoc = json_parseString(jsonText);

   if json_error();
      dsply json_message();
   endif;
```

```
   dcl-s pDoc pointer;

   pDoc = json_parseFile('/tmp/input.json');

   if json_error();
      dsply json_message();
   endif;
```

- `json_parseString` parses JSON (or XML) text already in a variable, `json_parseFile` reads it from a stream file on the IFS instead, only the source changes, everything else about `pDoc` afterward is identical.
- `json_error()` tells whether the last operation failed, `json_message()` then returns the actual error text (or, for the SQL routines below, the SQL error message).

## Reading values

```
   dcl-s companyName varchar(128);
   dcl-s blocked      ind;

   companyName = json_getStr(pCustomer : 'cucompanyname');
   blocked     = json_getBool(pCustomer : 'cublocked');
```

- `json_getStr`, `json_getNum`, `json_getInt`, `json_getBool`, `json_getDate`, ... each retrieve one value from a node, by node path expression.
- These names come directly from the SQL column names (or the JSON/XML document), not from our own naming convention, exactly like the field names covered in the XML parsing chapter.

## Building a document

```
   dcl-s pJournal pointer;

   pJournal = json_newObject();
   json_setStr(pJournal : 'olcompanyid' : companyId);
   json_setStr(pJournal : 'olorderid'   : orderId);
   json_setStr(pJournal : 'olactionid' : 'PLANNED');
   json_setStr(pJournal : 'oltext'     : 'Order added to batch ' + %char(batchId));

   WriteOrderJournal(pJournal);

   json_delete(pJournal);
```

- `json_newObject()` creates an empty object node, `json_setStr`/`json_setNum`/`json_setBool`/... each add one field to it.
- Every node created this way must eventually be released with `json_delete`, NoxDB does not garbage collect its nodes automatically.

### Arrays and json_copy_clone

```
   dcl-s pBatchOrders pointer;
   dcl-s pOrder       pointer;
   dcl-s quantities   int(5) dim(3);
   dcl-s i            int(5);

   quantities(1) = 10;
   quantities(2) = 25;
   quantities(3) = 5;

   pBatchOrders = json_newArray();

   for i = 1 to %elem(quantities);
      pOrder = json_newObject();
      json_setNum(pOrder : 'quantity' : quantities(i));

      json_arrayPush(pBatchOrders : pOrder : json_copy_clone);
      json_delete(pOrder);
   endfor;
```

- `json_newArray()` creates an empty array node, `json_arrayPush` appends one element to it.
- `pOrder` is reused as a scratch node on every pass of the loop: `json_copy_clone` tells `json_arrayPush` to copy `pOrder`'s current content into the array, instead of just linking to `pOrder` itself, this is why `pOrder` can safely be built again, and deleted, on the very next pass.


## Iterating over a node

```
   dcl-s orderIterator          likeds(json_iterator);

   orderIterator = json_setIterator(p_batch_orders);

   dow json_forEach(orderIterator);
      orderQuantity = json_getNum(orderIterator.this : 'ohquantity');
   enddo;
```

- `json_setIterator(node)` creates an iterator over the children of `node`, `json_forEach(iterator)` advances it and returns whether there was another element.
- `json_iterator` is a data structure type NoxDB provides, declared with `based` (an older alternative to `template`, see the Data structures chapter). `iterator.this` is a pointer to the current node, `iterator.isFirst`/`isLast`/`count`/`length` are also available.
- Iterators nest: iterating over one of `orderIterator.this`'s own child nodes just needs a second, independent `json_iterator`.

## Writing a document back out

```
   json_writeJsonStmf(pDoc : '/tmp/output.json' : 1208 : *off);
```

- `json_writeJsonStmf` writes a node tree straight to a stream file on the IFS: the node, the target path, the CCSID to write it in, and whether to write it human-readable (`*on`) or compact (`*off`).


## Writing the JSON to a variable

```
   dcl-s jsonText varchar(32767);

   jsonText = json_asJsonText(pDoc);
```

- `json_asJsonText` returns the node tree as a `varchar(32767)` value instead of writing it anywhere.
- `json_asJsonText16M` does the same but returns a much larger value (up to 16 MB), for a document too big to fit in a normal `varchar`.


## Cleaning up

Every node returned by `json_parseString`/`json_parseFile`/`json_newObject`/`json_newArray`/`json_sqlResultSet` needs to be released with `json_delete` once it is no longer needed. Wrapping the whole procedure in a `monitor`/`on-error`, with `json_delete`/`json_sqlDisconnect`/`json_close` in `on-exit` (see the Error handling chapter), is the safest way to make sure this always happens, even when something goes wrong.

```
   dcl-pi *n int(10);
      companyId varchar(64) const;
   end-pi;

   dcl-s pCustomer pointer;

   monitor;
      pCustomer = json_sqlResultSet('select * from customers where cucompanyid = ''' + companyId + '''');
      pCustomer = json_locate(pCustomer : '[0]');

      // ... work with pCustomer ...

      return OKAY;
   on-error;
      return ERROR;
   endmon;

   on-exit;
      json_delete(pCustomer);
      json_sqlDisconnect();
```

- Whichever `return` is reached, normal or from `on-error`, `on-exit` still runs afterward, `json_delete` and `json_sqlDisconnect` are guaranteed to happen exactly once.
- `json_delete(*null)` is harmless, so this pattern works even when the procedure fails before `pCustomer` was ever assigned.


## SQL integration : building a node tree straight from a query

A standout NoxDB feature: a `select` statement can be turned directly into a node tree, one object per row, without needing a cursor or a matching data structure.

```
   dcl-s pCustomer     pointer;
   dcl-s sqlStatement  varchar(4096);

   sqlStatement = 'select * from customers'
               + ' where cucompanyid = ''' + companyId + ''''
               +   ' and cucustomerid = ''' + customerId + ''''
               + ' fetch first 1 row only';

   pCustomer = json_sqlResultSet(sqlStatement);
   pCustomer = json_locate(pCustomer : '[0]');

   if pCustomer = *null;
      return ERROR;
   endif;

   on-exit;
      json_sqlDisconnect();
```

- `json_sqlResultSet(statement)` runs the query and returns the result as a node tree, `json_locate(node : '[0]')` picks out its first row.
- Releasing the SQL connection with `json_sqlDisconnect()` in `on-exit` (see the Error handling chapter) makes sure it always happens, whether the procedure returns normally or through an error.

### Parameters of json_sqlResultSet

```
   json_sqlResultSet(statement : start : maxRows : formatOptions : templateValues);
```

Only `statement` is required, the rest are optional, in this order:

| Parameter | Meaning |
| --- | --- |
| `statement` | The SQL statement to run. |
| `start` | The first row to return, `1` (the default) starts at the beginning. |
| `maxRows` | How many rows to return, or `json_ALLROWS` (the default) for all of them. |
| `formatOptions` | One or more of the constants below, added together, controlling the shape of the returned node. |
| `templateValues` | An object with values to substitute into placeholders in `statement`. |

By default (`formatOptions` omitted), the result is a plain array, one object per row, exactly like the examples above. Adding format options changes what comes back:

| Constant | Effect |
| --- | --- |
| `json_META` | Wraps the array in an object instead, the rows themselves move to a `rows` property, alongside a `metaData` property. |
| `json_FIELDS` | Adds column metadata under `metaData.fields` (implies `json_META`). |
| `json_TOTALROWS` | Adds the exact total row count as `totalRows` (implies `json_META`). |
| `json_APPROXIMATE_TOTALROWS` | Same as `json_TOTALROWS`, but faster and only approximate. |
| `json_UPPERCASE` | Column names are returned in upper case. |
| `json_CAMEL_CASE` | Column names are converted to camelCase, `THE_COLUMN_NAME` becomes `theColumnName`. |
| `json_SYSTEM_NAMES` | Uses the system (short) column names instead of the SQL names. |
| `json_GRACEFUL_ERROR` | On an SQL error, returns an object with `success = *off` and the error message, instead of `*null`. |

```
   dcl-s pOrders     pointer;
   dcl-s totalOrders int(10);

   pOrders = json_sqlResultSet(sqlStatement : start : maxRows : json_TOTALROWS);

   totalOrders = json_getInt(pOrders : 'totalRows');
   pOrders     = json_locate(pOrders : 'rows');
```

- Because `json_TOTALROWS` was requested here, the return value is now an object (not a plain array), with the row count under `totalRows`, and the rows themselves moved one level deeper, under `rows`, `json_locate(... : '[0]')` becomes `json_locate(... : 'rows[0]')` to still reach the first one.
- For exactly one row, `json_sqlResultRow` (singular) can be used instead of `json_sqlResultSet`, it returns that one row directly, without needing `json_locate(... : '[0]')` at all.
