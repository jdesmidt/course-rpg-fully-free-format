# Debugging

## Debug from VS Code

Debugging RPG directly from VS Code, with the Code for IBM i extension, is possible: it uses the exact same underlying IBM i debugger as the green-screen `STRDBG` covered below, just with a modern editor around it (breakpoints set by clicking in the margin, variables shown in a side panel, ...).

In practice, this needs the system's Debug Service Job to be started, and specific PTFs to be installed for the IBM i release in use. Many systems, especially ones that aren't kept fully up to date, simply don't have these applied yet, this is often the actual reason debugging from VS Code fails to connect, rather than anything wrong with the extension itself or its setup. Check with whoever manages the system before relying on it.


## Debug from green screen

The traditional way to debug, still available (and still working) everywhere, directly from a 5250 session.

```
   STRDBG PGM(MYLIB/MYPGM) UPDPROD(*YES);
```

- `STRDBG` starts the debugger for the named program. `UPDPROD(*YES)` allows debugging it even though it is a production object.
- The program must have been compiled with debugging data (the default), so the debugger has your actual source to show, not just a generated listing.

Once the debugger is started:

- **F6** sets (or removes) a breakpoint on the line the cursor is on.
- `CALL MYLIB/MYPGM` runs the program as usual, from the command line, execution stops as soon as it reaches a breakpoint.
- **F10** steps through the program, one statement at a time.
- **F11** displays the value of the field the cursor is currently on.
- **F12** resumes the program, running until the next breakpoint, or until the program ends.


## Debug a batch job

`STRDBG` above only works for a program running in your own job. A batch job (or any job other than your own) has to be debugged from a second, interactive session instead, using `STRSRVJOB` to attach to it.

Submit the job held, so it does not start running before the debugger is attached:

```
   SBMJOB CMD(CALL MYLIB/MYBATCHPGM) JOB(MYBATCHJOB) JOBQ(QBATCH) HOLD(*YES);
```

Find the job's number, and start servicing it, from a second session:

```
   WRKJOBQ QBATCH;                                    // find MYBATCHJOB, note its job number and user

   STRSRVJOB JOB(123456/JDESMIDT/MYBATCHJOB);
```

- `STRSRVJOB` lets this session debug (or otherwise service) another job, without being signed on to it.

Start the debugger and set a breakpoint, exactly like above, then release the job so it actually starts running:

```
   STRDBG PGM(MYLIB/MYBATCHPGM) UPDPROD(*YES);        // set a breakpoint with F6

   RLSJOB JOB(123456/JDESMIDT/MYBATCHJOB);
```

- `RLSJOB` releases the held job, it starts running, and stops as soon as it reaches the breakpoint. From here on, the same F10/F11/F12 keys as for interactive debugging apply.

Once finished:

```
   ENDDBG;

   ENDSRVJOB;
```

- `ENDDBG` ends the debug session, `ENDSRVJOB` stops servicing the other job and returns this session to normal.
