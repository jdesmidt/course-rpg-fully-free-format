# Xml parsing

`xml-into` is RPG's native operation for parsing an XML document straight into a data structure (or an array of data structures), matching elements and attributes to subfields by name. No external library is needed for this, unlike JSON (see the YAJL chapter), `xml-into` is a built-in RPG operation.


## Basic syntax

```
   xml-into result %xml(source : options);
```

- `result`: the data structure (or array) receiving the parsed values.
- `%xml(source : options)`: the XML document itself, and one string of blank-separated `option=value` pairs controlling how it is parsed.
- Subfields are matched to XML elements (or attributes) by name. A nested XML structure maps onto a nested data structure, a repeating element maps onto a `dim()`'d subfield or an array of data structures (see the Data structures chapter).
- Wrap `xml-into` in a `monitor`/`on-error` block (see the Error handling chapter): a badly formed document, or one that doesn't match the expected layout closely enough, raises an error instead of silently producing wrong data.


## Options

| Option | Values | Meaning |
| --- | --- | --- |
| `doc` | `string` (default), `file` | Whether the value passed to `%xml()` is the XML text itself, or a path to a file on the IFS. |
| `path` | e.g. `path=main/info/name` | Which element in the document to start matching from, elements are separated by `/`. Needed whenever `result` corresponds to an inner element, not the document's outermost one. |
| `case` | `any`, `upper`, `lower`, `convert` | How XML element/attribute names are matched against the data structure's subfield names. `any` ignores case entirely, `convert` also replaces characters that aren't valid in an RPG name (like `-`) with `_`. |
| `allowextra` | `yes`, `no` (default) | Whether the document may contain elements that don't exist in `result`, without that being an error. |
| `allowmissing` | `yes`, `no` (default) | Whether `result` may have subfields that are simply absent from the document, without that being an error. |
| `countprefix` | e.g. `countprefix=num_` | For a repeating element mapped onto an array, gives a matching field (prefixed as given) that receives the actual number of occurrences found, exactly like the `countprefix` option of `data-into` (see the YAJL chapter). |
| `ccsid` | a CCSID number, or `job` | The character encoding the document is in, when it differs from the job's own CCSID. |
| `trim` | `all` | Removes leading and trailing whitespace from a value before it is stored in a character subfield, off by default. |
| `ns` | `remove`, `merge` | How XML namespaces are handled: `remove` strips the namespace prefix entirely, `merge` keeps it but turns the `:` into a `_` instead. |
| `nsprefix` | e.g. `nsprefix=ns_` | Together with `ns=remove`, captures the namespace prefix that was stripped from an element into a matching field. |

- `allowmissing=yes` and `countprefix` both deal with "this element might not be there", `countprefix` is usually the better choice, since it tells you exactly what was (and wasn't) found, instead of just allowing something to be missing silently.


## Examples

### A flat document

```
   dcl-pi *n int(10);
      qrdata varchar(1024) const;
   end-pi;

   dcl-s xmloptions char(256) inz('doc=string allowextra=yes allowmissing=yes case=any ccsid=ucs2 path=QR');

   dcl-ds qrcode qualified;
      env  char(20);
      type char(64);
      user varchar(64);
      pasw varchar(64);
   end-ds;

   monitor;
      xml-into qrcode %xml(qrdata : xmloptions);
   on-error;
      return -1;
   endmon;
```

- `path=USER` starts matching from the `<USER>` element, so `qrcode`'s subfields (`env`, `type`, `user`, `pasw`) correspond to its children, not to the whole document.
- `allowextra=yes` and `allowmissing=yes` make this tolerant of a document that has a few more, or a few fewer, elements than `qrcode` expects.
- `ccsid=ucs2` tells the parser the incoming XML is Unicode (UCS-2), not in the job's own CCSID.

A matching XML document, passed in as `qrdata`, could look like this:

```xml
<QR>
   <ENV>PROD</ENV>
   <TYPE>LOGIN</TYPE>
   <USER>jdesmidt</USER>
   <PASW>Secr3t!</PASW>
   <SESSIONID>AB12CD34</SESSIONID>
</QR>
```

### A nested document with repeating elements

```
   dcl-pi *n int(10);
      xmldata    varchar(256000) value;
      deliveryid varchar(64);
   end-pi;

   dcl-ds idoc_data_ds qualified;
      dcl-ds e1edl20;
         vbeln             varchar(64) inz('');
         number_of_e1adrm1 int(10) inz(0);
         dcl-ds e1adrm1 dim(99);
            partner_q  varchar(4)  inz('');
            partner_id varchar(64) inz('');
         end-ds;
         number_of_e1edl24 int(10) inz(0);
         dcl-ds e1edl24 dim(99);
            posnr  varchar(64) inz('');
            matnr  varchar(64) inz('');
            werks  varchar(64) inz('');
            lgmng  zoned(13:3);
            meins  char(5);
            vgbel  varchar(64) inz('');
            vgpos  varchar(64) inz('');
            dcl-ds ze1edl24;
               zzfastflowcond varchar(256) inz('');
            end-ds;
         end-ds;
      end-ds;
   end-ds;

   dcl-s xmloptions char(256) inz('doc=string allowextra=yes allowmissing=yes case=any countprefix=number_of_ ccsid=ucs2 path=ZDELVRY07/IDOC');

   monitor;
      xml-into idoc_data_ds %xml(xmldata : xmloptions);
   on-error;
      return -1;
   endmon;
```

- `path=ZDELVRY07/IDOC` skips straight to the `<IDOC>` element inside the (SAP) `<ZDELVRY07>` message, ignoring everything else around it.
- `e1adrm1` and `e1edl24` are repeating elements, mapped onto `dim(99)` arrays of nested data structures, one occurrence per element found in the document.
- `countprefix=number_of_` is why `number_of_e1adrm1` and `number_of_e1edl24` get filled in automatically, with however many `e1adrm1`/`e1edl24` elements were actually present, no separate counting logic is needed.
- `ze1edl24` shows a data structure nested inside an array occurrence, itself with its own (non-repeating) subfield.

A matching XML document, passed in as `xmldata`, could look like this:

```xml
<ZDELVRY07>
   <IDOC>
      <E1EDL20>
         <VBELN>0080000123</VBELN>
         <E1ADRM1>
            <PARTNER_Q>WE</PARTNER_Q>
            <PARTNER_ID>CUST0001</PARTNER_ID>
         </E1ADRM1>
         <E1ADRM1>
            <PARTNER_Q>LF</PARTNER_Q>
            <PARTNER_ID>SUPP0002</PARTNER_ID>
         </E1ADRM1>
         <E1EDL24>
            <POSNR>000010</POSNR>
            <MATNR>MAT-1001</MATNR>
            <WERKS>1000</WERKS>
            <LGMNG>100.000</LGMNG>
            <MEINS>KG</MEINS>
            <VGBEL>0000045678</VGBEL>
            <VGPOS>000010</VGPOS>
            <ZE1EDL24>
               <ZZFASTFLOWCOND>URGENT</ZZFASTFLOWCOND>
            </ZE1EDL24>
         </E1EDL24>
         <E1EDL24>
            <POSNR>000020</POSNR>
            <MATNR>MAT-1002</MATNR>
            <WERKS>1000</WERKS>
            <LGMNG>50.000</LGMNG>
            <MEINS>KG</MEINS>
            <VGBEL>0000045678</VGBEL>
            <VGPOS>000020</VGPOS>
         </E1EDL24>
      </E1EDL20>
   </IDOC>
</ZDELVRY07>
```

- Two `<E1ADRM1>` and two `<E1EDL24>` elements come in, so after parsing, `number_of_e1adrm1` and `number_of_e1edl24` both end up as `2`, and `e1adrm1(1)`/`e1adrm1(2)` and `e1edl24(1)`/`e1edl24(2)` are filled in, the remaining occurrences (up to 99) are simply left at their initial value.
- The first `<E1EDL24>` has a nested `<ZE1EDL24>`, the second one does not, this is exactly what `allowmissing=yes` allows: `e1edl24(2).ze1edl24.zzfastflowcond` just stays blank.
