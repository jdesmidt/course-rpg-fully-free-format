# Error handling

## Callp(e) and error handling

Throughout this chapter, a procedure was always called directly by name, with no explicit operation code (`calcTotal(10 : 3)`). This is the normal way to call a procedure or a prototyped program in free format. The explicit `callp` operation is only needed to attach an operation code extender, such as `(e)`.

```
   callp(e) calcTotal(wPrice : wQty);

   if %error();
      dsply 'calcTotal failed';
   else;
      dsply 'calcTotal succeeded';
   endif;
```

- Without `(e)`, an unhandled error inside the called procedure or program (a numeric overflow, for example) also ends the caller.
- With `(e)`, that error is caught instead: `%error()` turns on, and the program simply continues with the next statement.
- `%status()` can be checked right after, to find out the specific error/status code.

```
   if %error();
      dsply %char(%status());          // numeric status code of the error
   endif;
```

- `(e)` is not limited to `callp`, the same extender exists on many file operations (`chain(e)`, `read(e)`, `update(e)`, ...), with exactly the same meaning: catch the error into `%error()` instead of ending the program.


## Monitor

`monitor` groups one or more statements together with one or more `on-error` blocks that catch an error in them, ending with `endmon`. Unlike `callp(e)`/`chain(e)` above, it is not limited to one single call, and it can distinguish between different kinds of errors.

### Catching every error

```
   monitor;
      wResult = wAmount / wDivisor;
   on-error;
      dsply 'something went wrong';
   endmon;
```

- The statements between `monitor` and the first `on-error` are the ones being watched.
- A plain `on-error;`, with no status code, is the same as `on-error *all;`, it catches every possible error.
- When an error occurs, control jumps straight to the matching `on-error` block, the rest of the monitored statements are skipped.
- When nothing goes wrong, every `on-error` block is simply skipped, execution just continues after `endmon`.

### Catching one or more specific status codes

Several `on-error` blocks can be chained, each for one or more specific status codes, the first one that matches is used, similar to separate `catch` clauses for different exceptions in other languages. `%status()` (see `callp(e)` above) still gives the precise status code of whatever error was actually caught.

```
   dcl-s wResult packed(9:2);

   monitor;
      wResult = wAmount / wDivisor;
   on-error 00102;
      dsply 'division by zero';
      wResult = 0;
   on-error *all;
      dsply %char(%status());          // any other error
   endmon;
```

- `on-error 00102` only catches status code `00102` (division by zero), any other error falls through to the next `on-error` clause.
- Several status codes can be listed together: `on-error (00102 : 00105);`.
- `*program` (status codes 100-999) and `*file` (1000-9999) group whole ranges of related errors at once, `*all` catches everything not caught by an earlier, more specific clause.

### on-excp

`on-excp` catches by the actual message ID (a CPF or MCH escape message, for example) instead of one of RPG's own numeric status codes. It is a newer addition (IBM i 7.4 TR6 / 7.5), and needs a runtime PTF on every system the program runs on. Any `on-excp` clause must be coded before the `on-error` clauses in the same monitor group.

```
   monitor;
      QCmdExc(command : commandLen);
   on-excp 'CPF9898';
      dsply 'command failed: invalid command syntax';
   on-error *all;
      dsply %char(%status());
   endmon;
```

- One or more message IDs can be listed, exactly like status codes on `on-error`: `on-excp 'CPF9898' : 'CPF2105';`.
- `on-excp(c)` limits it to messages sent directly by this procedure itself, not ones bubbling up from a program or procedure it called.
