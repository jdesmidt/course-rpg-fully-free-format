# Data structures

A data structure groups several subfields under one name. This is useful to keep related fields together, to structure the layout of data received from a file, a program call or an API, and to reuse an existing layout in multiple places.


## Internal data structures

An internal data structure is declared with `dcl-ds`, followed by the subfields and `end-ds`.

```
   dcl-ds wAddress;
      street char(30);
      city   char(20);
      zip    char(10);
   end-ds;

   wAddress.street = 'Main street 1';
   wAddress.city   = 'Brussels';

   dsply wAddress.city;
```

### qualified
- Subfields are addressed with the data structure name, a dot, and the subfield name.
- Add the `qualified` keyword when subfield names could otherwise clash with fields or subfields declared elsewhere in the program.

```
   dcl-ds wAddress qualified;
      street char(30);
      city   char(20);
      zip    char(10);
   end-ds;
```

### template

`template` marks a data structure as a pattern only, no storage is reserved for it, it exists purely so other data structures can reuse its layout with `likeds`. Template data structures are conventionally named with a `t_` prefix.

```
   dcl-ds t_address qualified template;
      street char(30);
      city   char(20);
      zip    char(10);
   end-ds;

   dcl-ds wHomeAddress likeds(t_address) qualified;
   dcl-ds wWorkAddress likeds(t_address) qualified;

   wHomeAddress.city = 'Brussels';
   wWorkAddress.city = 'Antwerp';
```

- `t_address` itself holds no data, and cannot be used on its own, only through `likeds`.
- Defining the shared layout once, as a template, is cleaner than reusing one of the "real" data structures as the pattern for the others (see `likeds`, right below).

### likeds

`likeds` creates a data structure with the exact same subfields as another, already declared, data structure. This avoids repeating the same subfields when a program needs several data structures with an identical layout.

```
   dcl-ds wHomeAddress qualified;
      street char(30);
      city   char(20);
      zip    char(10);
   end-ds;

   dcl-ds wWorkAddress likeds(wHomeAddress) qualified;
```

- Here `wHomeAddress` is a normal data structure, doubling as the pattern for `wWorkAddress`. When neither should be treated as "the original", define the shared layout once as a `template` instead (above), and `likeds` both from it.

### pos and overlay

By default, subfields are placed one after the other in memory. `pos` and `overlay` let you explicitly control where a subfield starts, so subfields can share (overlap) the same storage. This is typically used to reinterpret one field as several smaller ones, for example splitting a date received as a single character string.

```
   dcl-ds wDate;
      wDateChar char(8) inz('20260720');
      wYear     char(4) overlay(wDateChar);
      wMonth    char(2) overlay(wDateChar : 5);
      wDay      char(2) overlay(wDateChar : 7);
   end-ds;

   dsply wYear;                  // '2026'
   dsply wMonth;                 // '07'
```

- `overlay(field)` starts at the same position as `field`.
- `overlay(field : n)` starts at position `n` within `field` (position 1 is the first position).
- `pos(n)` places a subfield at absolute position `n` within the data structure, instead of relative to another subfield.

### Data structures and arrays combined

`dim` (see the Arrays chapter) can be combined with a data structure in two different ways, depending on whether the whole data structure needs to repeat, or just one of its subfields.

Putting `dim` on the data structure itself creates several occurrences of the entire layout, each occurrence has its own copy of every subfield.

```
   dcl-ds wEmployee dim(3) qualified;
      name   char(20);
      salary packed(9:2);
   end-ds;

   wEmployee(1).name   = 'Jurgen';
   wEmployee(1).salary = 3500.00;

   wEmployee(2).name   = 'Piet';
   wEmployee(2).salary = 3200.00;

   dsply wEmployee(1).name;
```

Putting `dim` on a subfield instead only turns that one subfield into an array, the rest of the data structure stays a single occurrence.

```
   dcl-ds wOrder qualified;
      orderNr  packed(7:0);
      lineDesc char(30) dim(5);
      lineQty  int(5)   dim(5);
   end-ds;

   wOrder.orderNr     = 1001;
   wOrder.lineDesc(1) = 'Keyboard';
   wOrder.lineQty(1)  = 2;

   dsply wOrder.lineDesc(1);
```

- On an occurrence of a data structure, the index comes right after the data structure name: `wEmployee(1).name`.
- On an array subfield, the index comes after the subfield name instead: `wOrder.lineDesc(1)`.
- `%elem` (see the Built-in functions chapter) works on both: `%elem(wEmployee)` returns the number of occurrences, `%elem(wOrder.lineDesc)` returns the number of elements of that subfield.


### Multi level data structures

A data structure can be built up out of several other data structures, several levels deep. There are two ways to do this: composing several separate `template`s with `likeds`, or nesting a `dcl-ds` directly inside another one.

#### Composing templates with likeds

Each level gets its own `template` (see above), which is then reused with `likeds` inside the next level up. This is the natural style for a document with a fixed, external structure, for example an SAP IDOC received as XML: the segment and field names below (`e1mastm`, `matnr_long`, `idnrk`, ...) come directly from SAP's IDOC definition, not from our own naming convention, since a technique like `xml-into` (see the XML parsing chapter) or `data-into` (see the YAJL chapter) matches subfields to the document by name.

```
   dcl-ds edi_dc40_ds qualified template;
      segment        char(1);
   end-ds;

   dcl-ds e1mastm_ds qualified template;
      segment        char(1);
      matnr_long     char(64) inz('');        // item number
   end-ds;

   dcl-ds e1stpom_ds qualified template;
      segment        char(1);
      idnrk          char(64) inz('');           // raw material item number
   end-ds;

   dcl-ds e1stzum_ds qualified template;
      segment        char(1);
      e1mastm        likeds(e1mastm_ds);
      e1stpom        likeds(e1stpom_ds);
   end-ds;

   dcl-ds sap_material_data_ds qualified template;
      edi_dc40       likeds(edi_dc40_ds);
      e1stzum        likeds(e1stzum_ds);
   end-ds;

   dcl-ds sap_material_data likeds(sap_material_data_ds);
```

- Each `_ds` is a template of just one level, `e1stzum_ds` nests `e1mastm_ds` and `e1stpom_ds`, `sap_material_data_ds` nests `edi_dc40_ds` and `e1stzum_ds` in turn, one `likeds` per level.
- Only the very last line, `sap_material_data`, is a real data structure, everything it is built from stays a template, no storage is reserved until this final `likeds`.
- The same source also defines a second, parallel tree for routing data, reusing `edi_dc40_ds` again, and including a `dim(99)` array of another template with a manually declared `number_of_...` field next to it, filled in by hand once the array has been read. This is exactly the same idea as the `countprefix` option covered in the XML parsing chapter, just written by hand instead of being filled in automatically by `xml-into`.

This is what the nesting actually looks like, once every `likeds` is followed all the way down:

```
sap_material_data                     (likeds sap_material_data_ds)
├── edi_dc40                          (likeds edi_dc40_ds)
│     └── segment                     char(1)
└── e1stzum                           (likeds e1stzum_ds)
      ├── segment                     char(1)
      ├── e1mastm                     (likeds e1mastm_ds)
      │     ├── segment               char(1)
      │     └── matnr_long            char(64)
      └── e1stpom                     (likeds e1stpom_ds)
            ├── segment               char(1)
            └── idnrk                 char(64)
```

- Every branch of the tree is one `template`, and every line connecting two branches is one `likeds`.
- A field several levels deep is addressed by chaining the dots all the way down: `sap_material_data.e1stzum.e1mastm.matnr_long`.

#### Nesting a data structure directly

When a sub-structure is only ever used inside its one parent, and never reused anywhere else, it can be declared directly inside the parent instead, without a separate template or `likeds`.

```
   dcl-ds delivery qualified;
      deliveryid      varchar(64) inz('');
      salesoffice     varchar(64) inz('');
      customerid      varchar(64) inz('');
      number_of_lines int(10) inz(0);
      dcl-ds lines dim(999);
         deliverylineid    varchar(64) inz('');
         rawmaterialitemid varchar(64) inz('');
         quantity          zoned(13:3);
         unit              char(5);
         // ... more fields ...
      end-ds;
   end-ds;
```

- `lines` is a data structure in its own right, dimensioned as an array of 999 occurrences, but it only exists as part of `delivery`, it has no name of its own that could be reused with `likeds` elsewhere.
- This is simpler than the template style above when the nesting is only needed once, but does not scale as well when the same sub-structure (or parts of it) needs to be shared between several parents.


### Sorting arrays of data structures

`sorta` (see the Arrays chapter) can also sort an array of data structure occurrences, using one of its subfields as the sort key.

```
   dcl-ds wEmployee dim(3) qualified;
      name   char(20);
      salary packed(9:2);
   end-ds;

   wEmployee(1).name = 'Jurgen'; 
   wEmployee(1).salary = 3500.00;

   wEmployee(2).name = 'Piet';   
   wEmployee(2).salary = 3200.00;

   wEmployee(3).name = 'An';     
   wEmployee(3).salary = 4000.00;

   sorta wEmployee(*).salary;

   dsply wEmployee(1).name;          // 'Piet', lowest salary first
```

- `(*)` after the array name means "every occurrence", followed by a dot and the subfield to sort on.
- Add the `(d)` extender to sort descending, exactly like a plain array: `sorta(d) wEmployee(*).salary;`.

#### Sorting on more than one subfield

`%fields()` sorts on more than one subfield at once, comparing them left to right, this requires IBM i 7.3 TR11 / 7.4 TR5 or later.

```
   sorta wEmployee %fields(salary : name);        // ascending, salary first, name as tie-breaker

   sorta(d) wEmployee %fields(salary : name);     // descending
```

- Unlike the single-subfield form above, `%fields()` is used directly on the array name, without `(*)`.


## SDS (Program Status Data Structure)

The Program Status Data Structure gives a program access to information about itself and the current error, such as the program name, the procedure name or the last error message. It is declared with the `psds` keyword.

```
   dcl-ds wPgmInfo psds qualified;
      pgmName   char(10) pos(1);
      status    *status;
      routine   *routine;
   end-ds;

   dsply wPgmInfo.pgmName;
```

- Predefined subfields can be positioned with `pos`, or filled automatically using special keywords like `*status`, `*routine` and `*proc`.
- There can be only one Program Status Data Structure per program or module.
- It is mainly used for error handling: to find out what went wrong and where, when an unexpected error occurs.
