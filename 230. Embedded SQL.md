# Embedded SQL

SQL statements can be written directly inside RPG source, this is embedded SQL. It is an alternative to the native file access covered in the previous chapter, especially useful for set-based operations, joins, and querying the many built-in IBM i Services.


## SQL in RPGLE

### EXEC SQL

Every embedded SQL statement starts with `exec sql`. In Fully Free Format RPG, no `END-EXEC` is needed, the statement simply ends with a semicolon, exactly like any other free-format statement.

```
   exec sql
      select firstName, lastName
        into :wFirstName, :wLastName
        from employees
       where empId = :wEmpId;
```

### Host variables : the colon (:)

Any RPG field can be used inside an SQL statement, prefixed with a colon, this is called a host variable. Above, `:wEmpId` supplies a value to SQL, `:wFirstName` and `:wLastName` receive values back from SQL.

### SET OPTION

`set option` changes precompiler options (like the ones normally set on the `CRTSQLRPGI` command) directly in the source. It must be the very first SQL statement in the program.

```
   exec sql set option naming = *sys, commit = *none, datfmt = *iso;
```

- `naming`: whether to write file references the *SQL way (`schema.table`) or the *SYS way (`library/table`).
- `commit`: the commitment control level, `*none` when the program does not use commitment control at all.


## Using SQL functions

A single SQL function can be used without a full `select`, using `set`.

```
   exec sql set :name = lower(:name);      // convert to lowercase
   exec sql set :name = upper(:name);      // convert to uppercase
```


## Select statement

### Fetch first row only

When exactly one row is expected, a plain `select ... into` retrieves it directly, without needing a cursor.

```
   exec sql
      select firstName, lastName
        into :wFirstName, :wLastName
        from employees
       where empId = :wEmpId
       fetch first 1 row only;
```

- `fetch first 1 row only` avoids an error when the query could technically return more than one row, only the first one is used.

### Checking whether a record exists

To just check whether a record exists, without needing any of its columns, select the constant `1` into a dummy field, and look at `sqlcode` instead of the field itself: `0` means a row was found, `100` means it was not.

```
   dcl-s    wExist         ind inz(*off);

   exec sql
      select 1
        into :wExists
        from customers
       where custNr = :wCustNr
       fetch first 1 row only;

   if wExist;
      dsply 'Customer exists';
   else;
      dsply 'Customer not found';
   endif;
```

- This is cheaper than `select count(*)`, since the database can stop looking as soon as it finds one matching row.

## Cursors

A cursor is needed as soon as a query can return more than one row that needs to be processed one at a time.

### Prepare and declare

A **static** SQL statement, known at compile time, is simply declared as a cursor directly:

```
   exec sql declare custCur cursor for
      select custNr, custName
        from customers
       where city = :wCity;

   exec sql open custCur;
```

A **dynamic** SQL statement, its text only known at run time (built up in a variable), needs an extra `prepare` step first:

```
   exec sql prepare stmt from :wSqlText;
   exec sql declare custCur cursor for stmt;
   exec sql open custCur;
```

### Fetch : row by row

```
   exec sql fetch next from custCur into :wCustNr, :wCustName;

   dow sqlcode = 0;
      dsply wCustName;
      exec sql fetch next from custCur into :wCustNr, :wCustName;
   enddo;

   exec sql close custCur;
```

### Fetch : multiple rows at once, into an array

Fetching many rows one at a time is slower than fetching a whole batch at once, into an array of data structures (see the Data structures chapter).

```
   dcl-ds wCustomer dim(100) qualified;
      custNr   packed(7:0);
      custName char(30);
   end-ds;

   exec sql fetch next from custCur for 100 rows into :wCustomer;
```

- `for 100 rows into :wCustomer` fills up to 100 occurrences of `wCustomer` in one round trip.
- The number of rows actually returned (which can be less than the array size, for the last batch) is available through `get diagnostics` (see below).


## SQLCODE vs SQLSTATE

- `sqlcode`: a numeric code, `0` means success, a positive value indicates a warning (e.g. `+100` means row not found), a negative value indicates a fatal error (e.g. `-206` for a missing column).
- `sqlstate`: a standardized 5-character string, the SQL industry standard for portability (e.g. `00000` is success, `02000` is no data found).


## Get diagnostics

`get diagnostics` retrieves details about the previous SQL statement, most commonly the number of rows it affected.

```
   exec sql
      update orders
         set status = 'SHIPPED'
       where custNr = :wCustNr;

   exec sql get diagnostics :wRowsUpdated = row_count;

   dsply wRowsUpdated;
```

- `row_count` works after an `insert`, `update`, `delete`, singleton `select into`, or `fetch`.


## Identity columns

An identity column (defined on the table as `generated always as identity` or `generated by default as identity`) automatically gets a sequential value from the database whenever a row is inserted, this is commonly used for a surrogate primary key. `identity_val_local()` retrieves the value that was just generated.

```
   exec sql
      insert into orders (custNr, orderDate)
        values (:wCustNr, :wOrderDate);

   exec sql
      select identity_val_local() as last_cod
        into :orderid
        from sysibm.sysdummy1;

   dsply orderid;
```

- `identity_val_local()` must be called right after the `insert` that generated the value, before any other `insert` happens on the same connection, otherwise it returns the value from that later `insert` instead.
- `sysibm.sysdummy1` is a system-supplied table with exactly one row and one column, used here only because `select` always needs a `from`, even when the value being selected does not come from a real table.


## IBM i Services

IBM i Services are system-supplied SQL views and table functions (mostly in schema `QSYS2`) that expose information about the system, jobs, objects, message queues and much more, all queryable with plain SQL.

```
   exec sql
      declare jobCur cursor for
         select job_name, job_status
           from table(qsys2.active_job_info()) x
          where job_status = 'MSGW';
```

- Select only the columns actually needed, rather than `select *`, IBM may add columns to these services over time.
